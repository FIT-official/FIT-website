# Fabrication services

Fabrication requests are a separate collection from 3D print quotes. A current, verified Pro subscription is required to publish services, show a public catalogue, calculate new estimates and accept new requests. Downgrading hides the public service but preserves both parties' access to existing jobs and the provider's ability to complete them.

Prices come from the provider's saved service, material and option choices. The server validates the submitted dimensions and selected options and stores the resulting price snapshot. It does not calculate geometry from the reference file or establish manufacturability. Manual services have a null estimated total and require a provider quote. Every job requires provider confirmation before work starts. Confirmed prices are SGD amounts agreed directly with the provider; these endpoints create no Stripe payment or FIT checkout.

## Catalogue and requests

- Owner GET `/api/user/fabrication-service?cursor=&limit=12` returns `{catalog, nextCursor, total, planId, canManage}`. Draft and enabled offers are included.
- Owner PUT accepts `{catalog:{enabled,offers},removedOfferIds:[]}`. Each save validates at most 24 offers and 24 explicit removals. It updates only these rows; offers on other pages remain unchanged. Offers are stored separately with a unique `(creatorUserId, offerId)` index, so there is no total service-variety cap. The response contains the saved page, not the complete catalogue. Global publishing and per-offer edits use last-write-wins; concurrent catalogue editing is not a collaborative merge workflow.
- Public GET `/api/creators/[id]/fabrication-service?cursor=&limit=12&offerId=` returns `{enabled,offers,creator,nextCursor,total}` when available or `{enabled:false}`. Only enabled offers of a currently verified Pro provider are exposed. `offerId` selects one offer directly without fetching all varieties.
- The former embedded catalogue, which was limited to 24 rows, remains readable and migrates on the first successful write. An atomic owner-scoped claim prevents concurrent first saves from restoring a removed legacy row. Other saves receive 409 before changing offers while the claim is active. Successful finalization matches the claim token and clears it. An uncertain migration failure retains the claim; an operator must quiesce writers, reconcile the legacy and offer rows, and complete the migration before clearing the claim. It never expires automatically while an earlier write might still finish. Ordinary multi-offer saves are bounded but not database transactions; a failure can leave part of a batch saved, so retry the same batch. No unseen offers are implicitly removed.
- POST `/api/fabrication/estimate` accepts `{creatorId,...input,imageAssetId?,referenceAssetId?}` and returns `{estimate:snapshot}`. It allows anonymous visitors when no customer-owned attachment is used.
- POST `/api/fabrication/requests` requires sign-in and also accepts a UUID `clientRequestId`. It returns `{request}` with status 201 on creation or 200 for an exact replay. Reusing that ID for different input returns 409. A database unique index prevents duplicate jobs. Request indexes are established before insertion, including when automatic index creation is disabled.
- GET `/api/fabrication/requests?role=provider|customer&cursor=&limit=20` returns `{requests,nextCursor}` scoped to the signed-in user. Maximum page size is 100. Cursors are opaque and ordered by descending creation time and request ID. Detail GET allows only the two parties.
- PATCH `/api/fabrication/requests/[requestId]` allows only the provider. It requires `expectedUpdatedAt` and accepts status, provider note, confirmed SGD price and revised personalization. The update compares the saved timestamp, revision and status atomically. A stale edit returns 409. The original image, customer personalization and estimate snapshot remain unchanged.

Monthly submissions share the existing creator print-request allowance. The initial counter includes both `CustomPrintRequest` and `FabricationRequest`. Duplicate concurrent submissions release their redundant reservation. Definitive failed writes release it; ambiguous database/network failures retain it because the insert may still commit. Operational reconciliation may be needed after such failures, rather than risking an understated usage count.

## Private attachments

Set `FABRICATION_S3_BUCKET_NAME` to a dedicated private bucket. The application refuses to fall back to a shop/public-media bucket. The API checks that **all four S3 Block Public Access settings** are true before upload or signed URL generation, caching the check for 60 seconds. The runtime role needs `s3:GetBucketPublicAccessBlock`, `s3:GetObject` and `s3:PutObject` for this bucket. Enable CORS GET/HEAD for the deployed application origins so the image editor can read signed previews; keep anonymous bucket/object access blocked. Cloud provisioning is a deployment step and is not performed by this change.

POST `/api/fabrication/assets` accepts one multipart `file`, up to 3 MiB. PNG/JPEG/WebP images must decode within 4096 pixels per dimension and 16 million pixels total. Images are re-encoded to WebP with metadata removed. STL, OBJ, 3MF and PDF are accepted as reference files after bounded format checks, served as attachment downloads rather than inline documents. DXF, SVG, HTML and remote image URLs are unsupported. Reference validation does not prove that a file is production-ready.

Assets use opaque IDs, owner-scoped storage keys and five-minute signed URLs. Only the asset owner, a participant in a request using the asset, or a visitor to the exact published template of a verified Pro provider can obtain a URL. Public templates must be images owned by that provider. Request reference files must be owned by that customer. Customer images can use any valid text region; an exact published template constrains customer text to its permitted region. Providers may adjust the region during review while retaining the original customer layout.

Storage attempts are limited to 50 per user per UTC day using an atomic reservation, plus 10 uploads per minute. These are operational limits, independent of the number of service varieties. Uploads whose database persistence or storage result is uncertain are retained privately for operator/lifecycle reconciliation. There is no immediate client-triggered delete: deletion could race a submitted job and destroy a referenced file. Configure retention and cleanup before production use, preserving any object referenced by a saved catalogue or request rather than expiring every object under the shared prefix.

## Deployment and verification

Production public reads, estimates, writes and uploads require working Upstash Redis settings. Missing configuration, limiter errors and limiter timeouts fail closed with 503. The development-only in-memory fallback is bounded and is not used in production. Clerk, MongoDB and live creator entitlement verification must also be configured. Keep existing job history available when subscriptions expire.

Focused automated coverage exercises tenant isolation, Pro gating, downgrade access, server price authority, manual pricing, immutable customer inputs, concurrent duplicate submissions, bounded uploads, private image access, atomic quotas, cursor pagination, and saving 60 service varieties without losing unseen rows. Database, authentication, Stripe entitlement and S3 calls are mocked in these tests; real Sharp image decoding and the domain validators/pricing functions run. These checks do not substitute for a deployed test with the production bucket, MongoDB indexes, Redis and a real Pro account.
